# Atualização do autarkjs.org para Autark 5.0.0

**Decisão recomendada:** migrar o guia e o tutorial para a API 5.0 com edição e reexecução na própria página; publicar a galeria do monorepo como um aplicativo estático de múltiplas páginas, sem um segundo catálogo de demos; atualizar os três casos de uso a partir do mesmo commit do Autark. Começar com pacotes empacotados localmente e só publicar o site depois de validar os pacotes oficiais e a compatibilidade da gramática.

**Base da análise:** site `cffa0af` (`relase/v5.0.0`), com seis pacotes Autark em **4.1.1** e `autk-grammar` em **5.6.0** no lockfile; Autark local `7dc7dea6cf860d8a9eb6c1ac2a5f64b450865460`, comparado à tag `@urban-toolkit/autk@4.1.1`. Os manifests do monorepo ainda dizem 4.1.1 e não havia tag 5.0.0 no checkout. O hash analisado é uma referência de desenvolvimento, não uma versão publicada. Nenhuma alteração funcional foi feita no site nem no monorepo.

## 1. Bloqueios e riscos de lançamento

| Prioridade | Achado e impacto | Ação |
| --- | --- | --- |
| P0 | `guide/autk-map/interactions.md`, os exemplos antigos e os **três apps** publicados usam `MapEvent.PICKING` e/ou `isPick`; essa interface foi removida. Um build pode passar e a ação não disparar no navegador. | Migrar para `MapEvent.CLICK` + `isClick`, mostrar o gesto real (duplo clique no snapshot) e testar seleção, hover e limpeza separadamente. |
| P0 | `guide/autk-map/terrain.md` chama métodos removidos; o guia DB passa opções antigas de CRS. | P0 | O shader antigo de **Shadows** associa `geometry.coordinates` a uma matriz; o compute atual rejeita esse caminho. O upstream já tem shader topológico e comportamento novo para linhas com vários segmentos. | Importar `compute.ts` e `shadow.wgsl` juntos, comparar resultados com fixtures e documentar diferenças esperadas. |

| P1 | `CodePlayground.vue` limpa DOM/canvas e chama `destroy()` só nas instâncias de Grammar que rastreia; não gerencia sistematicamente mapas, gráficos e outros recursos do código imperativo. Inserir o tutorial atual nele sem adaptação também perde `ctx` e não resolve imports externos automaticamente. | Definir o ciclo de vida de execução antes da migração. **Pré-release sem npm público.** Fixar um SHA para a integração. Em ambiente temporário, rodar o build do monorepo e empacotar os seis módulos (`npm run pack:packages`); instalar os seis tarballs no checkout descartável do site, conferir `npm ls` e garantir que código local não seja substituído pelo 4.1.1 público por deduplicação ou dependência transitiva. Como os manifests ainda usam 4.1.1, preparar versões distintas e coerentes em checkout isolado se necessário. Não commitar URLs `file:`, symlinks, lockfile experimental nem publicar pacote para fazer o teste. Exercitar export conditions, WASM e workers com o artefato real. A CI atual do site usa Node 22 e o checkout upstream exige Node ≥26.11.1/npm ≥12.2.0: separar o ambiente de empacotamento do teste de consumo e validar também no Node 22 usado pelo deploy atual. Depois da publicação oficial e da tag coordenada, rodar `npm run release:prepare -- --version 5.0.0 --dry-run`, então o preparo real. O aplicativo/site publicado não deve exigir `../autark`.

## 2. User Guide e referência de API

O guia já tem **65 instâncias de `CodePlayground`** na introdução e nos quatro módulos narrativos. A estrutura modular serve; não é necessário reescrever tudo. Atualizar os capítulos em que o contrato mudou, cobrir as lacunas abaixo e deixar os detalhes avançados na referência, galeria ou tutorial. `guide/recipes/index.md` ainda anuncia receitas futuras: usar o tutorial novo como próximo passo, em vez de criar seis cópias dos mesmos fluxos. `guide/index.md` e `HomeQuickStart.vue` também devem refletir o fluxo versão 5: o mapa pode funcionar sem servidor de tiles próprio, mas também aceita serviços opcionais de imagery/elevação; alinhar o trecho exibido com o código que realmente roda.

| Superfície | Revisão obrigatória e resultado didático |
| --- | --- |
| **Intro / core** — `guide/introduction.md`, novo tópico transversal | Ensinar `crs` do workspace versus `sourceCrs` da entrada. DB assume fonte EPSG:4326 por padrão; `map.loadCollection` sem `sourceCrs` espera dados já no CRS do mapa. Alinhar DB e mapa, sem reprojetar duas vezes. Incluir exemplo editável de GeoJSON bruto versus saída do DB, referência a `DEFAULT_WORKSPACE_CRS`, `DEFAULT_SOURCE_CRS` e registro de CRS; explicitar `geometryIndex` nas partes de edifícios. |
| **DB** — `workspaces`, `loading-data`, `retrieving-data`, `analyzing-data`, `updating-tables` | `db.setWorkspace(nome, { crs, precisionGrid })`; `sourceCrs` no topo dos cinco loaders, não dentro de `geometryColumns`/`autoLoadLayers`; `maxRasterCells` em vez de `maxPixels`. Preferir PBF local para o primeiro exemplo, apresentar Overpass configurável separadamente e mostrar filtros/tag sets em extratos. Em heatmaps, contrastar contagem de linhas (default ou `count(*)`) e valores não nulos por coluna; demonstrar `smoothingSigma` desligado e ligado, e o efeito de NoData. Revisar exemplos de update por chave e preservar `getRaster`, ainda válido. |
| **Map** — `index`, `layers`, `terrain`, `interactions`, `styling`, `thematic` | `new AutkMap(canvas, { showUi: false, crs })`; `isClick`/`isHover`, `setSelection`, `setHover`, `setSkipped` (substitui conjunto inteiro, `[]` limpa), `activeClickLayer`, tooltip opcional; filtrar eco do hover (`source: 'pointer'`) entre views. Trocar wrappers removidos por `loadTerrain({ source: { collection, property } })` e `removeTerrain()`. Explicar `setView` antes de tiles/terreno em mapa vazio, `loadTiles`, terreno fixo versus streaming, atribuição, `fitBounds` e câmera ortográfica persistente. Incluir raster RGB, ordem de desenho distinta da elevação e paletas customizadas; remover `poster` (ausente no código atual) e usar os presets válidos de `MapStyle`. |
| **Plot** — `index`, `chart-types`, `transformations`, `interactivity` | Atualizar `ticks.x/y.format`, `ticks.dimensions`, `style.columnFormats` e `style.colorMap` no lugar das opções antigas de topo. Demonstrar gráfico estático/`width: 'auto'` e um fluxo editável mapa ↔ dois gráficos: seleção persistente, hover transitório, `extent` da brush, compartilhamento proporcional (`shares`) e limpeza. Explicar proveniência, `autkIds` versus relações ponderadas, `boolean`/`subset`/custom, bins vazios/valores ausentes, filtros e top-K. Atualizar lista de gráficos e transforms; deixar `registerPlot`, `registerTransform` e seus validadores em um capítulo avançado curto, ligado ao caso Provenance. |
| **Compute** — `computing-properties`, `render-analysis`, `patterns` | Ensinar `variableMapping: { road: 'geometry' }` e acesso aos nós e pontos em WGSL; não declarar a geometria em `attributeMatrices`. Usar fixture pequena com linha multipartes para mostrar por que não se ligam partes distintas. Confirmar `ComputeRender` com classes, objetos e `building-windows`, identificar resultado por `windowId` e `sourceFeatureIndex` (não pelo índice de seleção do mapa), e migrar o padrão de picking. |
| **API / Grammar** — `guide/api/`, `guide/grammar/`, `.vitepress/config.ts` | Gerar os cinco módulos juntos, auditar links e âncoras removidos e corrigir sidebar e sintaxe Markdown gerada; não editar páginas TypeDoc como fonte primária. Validar todos os specs publicados contra o schema e o runtime selecionados. Não fazer busca-e-substituição de `coordinateFormat` em Grammar: é uma propriedade da especificação atual, distinta da opção direta da API DB. |

**Contrato do editor compartilhado.** Manter Run/Reset, saída de console ou DOM, mounts nomeados e indicação de WebGPU. Hoje o editor concatena abas, remove apenas imports nomeados por regex e executa `AsyncFunction`; não é compilador TS nem bundler. Para v5, manter exemplos executáveis em JS/ESM suportado explicitamente, separar código visível de setup repetitivo e expor dependências adicionais de maneira declarada (D3/GeoTIFF quando necessário), sem depender de hoisting transitivo. Preferir exemplos autônomos; para os encadeados, estado limitado ao capítulo e uma forma explícita de executar os pré-requisitos em ordem. Gerenciar disposers, abortar/inutilizar trabalho obsoleto e não deixar resultados da execução anterior sobrescreverem a atual. Testar **editar → executar → resultado mudar → resetar → repetir** para console, mapa, plot, compute e Grammar; incluir navegação, múltiplos exemplos na mesma página e falha recuperável. Carregar tarefas caras sob demanda. Não incluir códigos complexos da galeria automaticamente nesse executor.

## 3. Galeria espelhada

O site mantém 14 páginas `guide/gallery/ex*.md`, cards repetidos em `GalleryPageGrid.vue` e `HomeGallery.vue` e mais uma lista na sidebar. A home atualmente comenta `HomeGallery` e `HomeCaseStudies`. O upstream tem **35 exemplos** em cinco grupos (6 carregamento, 6 recursos básicos do mapa, 6 imagery/terreno, 9 plots e 8 analytics). A fonte já separa `catalog.ts`, páginas/variantes em `gallery/src/`, trechos **API in focus** (`code.ts`) e **Minimal runnable example** (`source.ts`). Isso atende ao objetivo de mostrar código legível sem exigir editor no site.

**Arquitetura recomendada:** sincronizar a árvore da galeria de um SHA com um comando explícito e verificável; compilar as páginas em `/gallery/apps/` com entrada de índice + cada caminho do catálogo. Usar o catálogo sincronizado para a capa VitePress `/gallery/` e para eventuais destaques na home, sem duplicar títulos, descrições, tags ou demos. Manter o HTML interativo upstream como destino (não colocar editor ou converter cada exemplo em Vue). A capa deve oferecer navegação do site; as demos devem oferecer um retorno claro à galeria. Preferir snapshot versionado com proveniência, ou um artefato de revisão preso por hash e verificado; evitar fetch de `main` no deploy. Dar preferência a implementar a portabilidade upstream para reduzir patches locais.

- **Rotas antigas:** candidatos `ex1→D01`, `ex2→S01`, `ex3→D06`, `ex4→P01` (ou `P09`), `ex5→A05`, `ex6→S04`, `ex7→I01`, `ex8→P02`, `ex9→P03`, `ex10→A01/A02`, `ex11→P06`, `ex15→A06`, `ex16→A08`, `ex17→A07`. Confirmar equivalência antes de redirecionar; quando mudar a atividade (por exemplo OSM live vs PBF, ou análise por janelas), manter uma página curta com contexto e destino em vez de um redirect silencioso. Manter `timeseries-click.html` upstream se for publicado como alias. Remapear referências da sidebar/guia; aposentar cards e imagens antigas só depois de inventariar referências, inclusive Grammar.
- **Assets e runtime:** isolar os dados da galeria ou reutilizar arquivos comprovadamente idênticos em bytes e licença, nunca só por nome. São ~59 MB na galeria upstream versus ~77 MB de dados públicos atuais do guia e ~29 MB no tutorial upstream completo. Os programas da galeria usam `BASE_URL` em vários pontos, mas `source.ts` produz exemplos com `/data/...` fixo; validar as URLs dos exemplos exibidos e as que a demo executa. Preservar atribuição dos tiles e avisos de rede. Verificar workers/WASM da DB ao lado do chunk servido, PBF/TIFF e navegação entre detalhes/variantes no prefixo real. Validar demos com apenas dados locais separadamente das que dependem de provedores externos.
- **Aceite:** cada entrada do catálogo e alias pretendido está publicado, pesquisável e tem código destacado; teste de produção percorre todos os links e assets obrigatórios. Em Chrome com WebGPU, verificar primeira renderização das 35 e interações representativas de cada grupo, com foco adicional em P03/P09, T02/T03 e A05–A08. Atualizar `AGENTS.md` e a skill `add-gallery-example` depois de mudar a arquitetura.

## 4. Tutorial de Urban Visual Analytics

Hoje o menu `Tutorial` vai para Observable. A fonte a migrar é `../autark/tutorial/`: introdução, formatos, DB, mapa, plot e compute têm **45 células editáveis** ao todo; `urbane.html` é um projeto final separado. A infraestrutura upstream tem estado compartilhado em `window.ctx`, fila de execução, dependências por célula, persistência local e fallback de Overpass com gravações e manifesto. Não transportar HTML, shell/CSS e CodeMirror como um segundo motor do site.

**Proposta:** criar `/tutorial/` com landing e capítulos Markdown nativos, sidebar de progresso, resumo do objetivo, tarefa editável, resultado esperado e próximo passo. Em mobile empilhar editor e resultado sem scroll horizontal da página; em telas largas usar espaço adicional nos capítulos visuais. Usar o tema claro/escuro do VitePress. Agrupar células que dependem da mesma preparação em um `CodePlayground`, com setup declarativo e, só quando útil, abas. Mostrar o que é pré-requisito, o que pode ser editado e o que será reinicializado. Decidir se edição persistente entre navegações justifica suporte compartilhado; caso implementada, associar à versão do snippet e permitir reset. Evitar `window.ctx` e alterações concorrentes do `fetch` global pelo fallback original; usar caminho local/PBF para a experiência principal e separar demonstração do serviço live, ou integrar replay com fronteira testável. Não prometer uso totalmente offline: DuckDB pode baixar extensão na primeira execução.

Preservar créditos e links aos notebooks originais; mover o destino principal do menu para o tutorial interno, mantendo Observable como fonte/histórico. ## 7. Sequência e critérios de saída

1. **Fixar candidato e matriz de dependências (bloqueante).** SHA e tarballs reproduzíveis; `npm ls` sem mistura involuntária de versões; escolha explícita para Grammar. Validar consumo e assets no Node do deploy. Especificação curta da estratégia de sincronização e versões.
2. **Migrar editor e uma fatia vertical do guia.** Primeira lição pequena DB → mapa → plot, com edição e reset realmente exercitados; depois distribuir a migração por DB/core, map, plot e compute. Rodar build e browser smoke a cada fatia. Regenerar TypeDoc e validar links junto com a migração de API.
3. **Espelhar a galeria e reimportar os três apps (em paralelo após 1).** Primeiro provar build com uma demo local/PBF, uma com tiles e um app com WASM; depois validar catálogo completo e rotas. Rodar `npm run build` e `npm run test:usecases`; adicionar teste estrutural de galeria e a matriz browser da seção 5. Separar mudanças de análise/resultado de ajustes de publicação.
4. **Converter o tutorial por capítulo (após o contrato do editor).** Começar por formatos + DB, depois mapa + plot e compute + projeto final. Cada entrega deve funcionar sem editor paralelo, com dados autorizados e saídas verificadas. Redes/FGV podem andar em paralelo; vídeo depende do arquivo e aprovação editorial.
5. **Homologar o artefato final.** Instalação limpa no Node do deploy, referências e links, `npm run build`, `npm run test:usecases`, `git diff --check`, smoke real de guia/Grammar/galeria/apps em preview, revisão mobile/dark/teclado e revisão humana dos resultados analíticos. Verificar compatibilidade novamente com os pacotes oficiais. Sem mudanças de GitHub Actions, push, merge em `main` ou deploy sem autorização explícita.

### Verificações realizadas nesta análise

- **Site atual (4.1.1):** em cópia limpa de `cffa0af`, `npm ci`, inspeção de dependências (Grammar **5.6.0** e módulos **4.1.1**), `npm run build` e `npm run test:usecases` passaram (6/6; build avisa sobre chunks grandes). O `node_modules` preexistente no checkout principal estava com Grammar **4.2.0** inválido para o manifest; não usar esse build local como baseline de Grammar.
- **Galeria upstream:** build Vite padrão em diretório temporário passou, mas gerou apenas o HTML do índice — prova do problema de empacotamento, não de falha das demos em dev.
- **Tutorial upstream:** `cd ../autark && node --test tutorial/test/*.test.mjs` passou 11/11. A execução de `node tutorial/test/browser.mjs` em Chrome chegou ao final das células dos capítulos e mostrou geometria não vazia nos mapas; a execução total atingiu o limite de 90 s enquanto `urbane.html` ainda importava dados. Em rodada isolada com tempo suficiente, `node tutorial/test/browser.mjs urbane.html` passou: carga, recomputação do score e drill-down/up do app do **tutorial**. Os testes usaram os bundles disponíveis no ambiente upstream, não um pacote npm 5.0.0 nem o wrapper do site.
- **Não verificado:** build do site com tarballs do candidato, rodada completa dos apps com WebGPU e assertivas analíticas, uma versão de Grammar compatível com os módulos Autark 5, vídeo/logos finais e teste de produção após migração. Nenhum desses itens deve ser dado como aprovado com base nos resultados acima.
